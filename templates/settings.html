System Architecture

The system employs a strictly decoupled architecture designed to prevent monitoring failures caused by host sleeping: 

                        GitHub Actions
                              |
                              | Scheduled cron (every 10-15 mins)
                              v
                      Monitoring Script (monitor.py)
                        /     |     \
                       /      |      \
                      v       v       v
              Website 1   Website 2   Website 3
                      \       |       /
                       \      |      /
                        Website 4
                              |
                              v
                    PostgreSQL Database (Shared)
                              ^
                              |
                              | Reads data & manages targets
                              v
                    Flask Dashboard (Render / Local)
Key Architectural Principle: The Flask dashboard does not run a permanent loop and is not responsible for keeping other services awake. GitHub Actions performs scheduled runs in an isolated runner, records results to the shared PostgreSQL database, and terminates cleanly.

Keep-Alive vs. Uptime Monitoring Disclosure

Periodic requests generated by GitHub Actions serve two distinct purposes:

  1. Keep-Alive Ping: Free hosting tiers (such as Render) suspend containers after 15 minutes of inactivity. Periodic GET requests wake sleeping processes or reset idle timers to minimize latency for human visitors.
  2. Availability Verification: Records whether the endpoint returns an acceptable HTTP status (2xx/3xx) and tracks response latency.
Realistic Limitation: Keep-alive requests do not guarantee 100% uptime. Services may still experience unexpected crashes, provider maintenance windows, deployment interruptions, or regional cloud outages between scheduled checks.
